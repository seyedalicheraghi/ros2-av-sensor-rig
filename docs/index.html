Docker Scaffold Plan

Project: ros2-av-sensor-rig — ROS2 multi-sensor data collection rig (Velodyne VLP-16, ArduCam UVC, Intel RealSense D415).
Author: Seyed Ali Cheraghi · source on GitHub

1. Goal

Containerize the full ROS2 runtime so the host stays clean, sensor SDKs are pinned to known-good versions, and recorded rosbags are reproducible across machines and over time.

2. Defaults Chosen

DecisionChoiceWhy
ROS2 distro Humble Hawksbill default LTS until May 2027; broadest driver coverage (Velodyne, RealSense, usb_cam all stable on Humble).
Base image ros:humble-ros-base Smaller than desktop-full; we add only the packages we need.
Compose vs single image Docker Compose Lets us split bringup, recorder, and foxglove so the recorder can be restarted without touching live drivers.
DDS implementation Cyclone DDS Industry default for ROS2; better multicast behavior than the FastDDS default in containerized setups.
GUI strategy X11 socket and Foxglove Studio RViz works locally via X11; Foxglove gives a browser UI for remote viewing — no commitment needed up front.
Bag persistence Bind-mount ./rosbags Recordings survive container restarts and are inspectable from the host.
Bag format MCAP (via rosbag2-storage-mcap) Industry-standard for autonomy data; works natively with Foxglove. SQLite3 is still available as fallback.

4. Hardware Passthrough Strategy

SensorMechanismWhy this and not something else
Velodyne VLP-16 network_mode: host The sensor blasts UDP on a fixed port; bridged networking would drop packets at high rate.
RealSense D415 /dev/bus/usb mount + udev rules on host librealsense talks raw USB; we need the bus device, not just /dev/video*.
ArduCam UVC /dev mount + symlink rule Standard V4L2 path. Symlink keeps device name stable.
Display (RViz) /tmp/.X11-unix + DISPLAY env Cheapest path on Linux; no GPU passthrough required for basic viz.

5. Typical Workflow

xhost +local:docker
docker compose -f docker/docker-compose.yml build
docker compose -f docker/docker-compose.yml up -d bringup
docker compose -f docker/docker-compose.yml exec bringup bash

# Inside the container:
colcon build --symlink-install
source install/setup.bash
ros2 launch vehicle_bringup full_stack.launch.py

# Optional: start the recorder in its own container
docker compose --profile record up -d recorder

# Optional: start Foxglove for browser-based viz
docker compose --profile viz up -d foxglove

6. Dev Containers (VS Code Extension)

The Dev Containers extension (ms-vscode-remote.remote-containers) lets VS Code attach its UI to a running container while the editor backend, language servers, terminals, and debuggers all execute inside that container. The host only runs the VS Code window; everything else (compilers, ROS2, Python interpreter, sensor SDKs) lives in the image defined by docker/Dockerfile.

In this project, opening the repo in VS Code triggers .devcontainer/devcontainer.json, which reuses the bringup service from docker-compose.yml. The result: one click gives you an editor whose colcon, ros2, and rclpy all match the container exactly — no second toolchain to keep in sync on the host.

ConcernWhat Dev Containers gives you
Reproducibility Every contributor edits against the same ROS2 Humble image, same DDS implementation, same sensor SDK versions. No "works on my machine" drift.
Host hygiene No need to install ROS2, librealsense, or Velodyne deps on the host. Removing the container removes everything.
IntelliSense accuracy The C++ and Python language servers see the real headers (/opt/ros/humble/include/...) so autocomplete and go-to-definition actually work for ROS2 symbols.
Pre-wired tooling The customizations.vscode.extensions block auto-installs the ROS, Python, C++, CMake, and YAML extensions inside the container on first open.
Same runtime as docker compose Because the dev container is the bringup service, anything that runs from a VS Code terminal behaves identically to docker compose exec bringup — including hardware passthrough.

Usage: install the Dev Containers extension in VS Code, open this repo, then run Dev Containers: Reopen in Container from the command palette. VS Code starts the compose stack, attaches to bringup, and drops you into /workspace as the ros user.

7. Tradeoffs & Things to Revisit

  • privileged: true — convenient for dev; production should narrow to explicit --device and cap_add entries.
  • No GPU reservation by default — add an NVIDIA runtime block when RealSense post-processing or large RViz scenes need acceleration.
  • Single image for all three services — keeps build cache hot. We can split per-sensor images later if vendor-SDK update cadence diverges.
  • Cyclone DDS pinned via env — if the host ROS2 install uses FastDDS, topic discovery may fail until both sides match.
